# Example: Protocol Buffers as a message format

This example shows an example, where an API artifact whose contract
methods use **protoc-generated types** as parameters and return values, and
the **proto serializer** plugin that converts those types to and from bytes
on the wire. Two components — `calculator` and `gateway` — talk to each
other over this API, in separate processes, over real HTTP, with every
byte on the wire actually protobuf-encoded.

It demonstrates three things: what a `.proto` file and its generated
types look like inside a contract, what a message-format API artifact's
`.itara` metadata needs to declare, and how the proto serializer plugin
gets wired onto a connection.

## What this demonstrates

`calculator`'s contract method is:

```java
CalculatorResponse add(CalculatorRequest request);
```

`CalculatorRequest` and `CalculatorResponse` are not hand-written — they're
generated by `protoc` from `calculator.proto` at build time. The contract
interface itself is still a plain, hand-written Java interface, the message
format only changes what the parameter and return *types* are,
not the shape of the interface, and not anything about how
`CalculatorServiceImpl` implements it. Open
`calculator-impl/.../CalculatorServiceImpl.java`: there is nothing
protobuf-specific in it at all. It reads `request.getA()` and
`request.getB()`, builds a `CalculatorResponse`, and returns it — exactly
like it would with any other Java object.

The serialization itself happens entirely in the proto serializer plugin
(`itara-serializer-protobuf`), loaded at runtime like any other serializer
— nothing here required writing new serializer code. It converts any
`GeneratedMessageV3` to bytes via `toByteArray()`, and back via reflection
on the target type's `parseFrom(byte[])` — generically, with no knowledge
of `CalculatorRequest`/`CalculatorResponse` specifically.

`gateway` deliberately does **not** use protobuf for its own contract —
its `sum(int, int)` method is plain int parameters, no message format
declared at all. This is the point: only `calculator`'s API opted into a
message format. `gateway` calls it through an ordinary-looking
`CalculatorService` reference and has no idea, and no reason to care, that
the bytes underneath are protobuf rather than JSON.

## Layout

```
protobuf-serializer/
  calculator/                 ← component parent
    calculator-api/           ← contract + calculator.proto + generated types
    calculator-impl/          ← business logic + activator
  gateway/                    ← component parent
    gateway-api/               ← plain contract, no message format
    gateway-impl/              ← business logic + activator; calls calculator
```

Two components, monorepo-style: each has its own parent aggregating an
`-api` and an `-impl` module, and one root `pom.xml` ties the two component
parents together.

## The metadata: what actually needs to be declared

**`calculator-api/calculator-api.itara`** — this is the file that matters
most for this example:

```toml
[contract]
message-format = "protobuf"

[serializers]
supported = [
  { id = "protobuf", version = "0.1.x" },
]
```

- `[contract] message-format` declares that this API's types are
  protoc-generated, not hand-written (ADR 0019). It's a property of the
  *contract*, independent of which serializer a given connection ends up
  using.
- `[serializers] supported` is optional, advisory metadata for tooling
  (`itara verify`) — it says which serializer ids/version ranges this
  artifact is known to work with. It does not gate anything at runtime;
  the agent will happily wire any serializer id a connection names. Try
  removing it: `itara verify` still runs clean, because the *capability*
  path (below) also confirms compatibility on its own.

**`itara-serializer-protobuf.itara`** (the serializer plugin's own
metadata — already published alongside the plugin itself, not part of
this example) is what makes the capability path work:

```toml
[serializer]
type = "protobuf"

[serializer.capabilities]
message-formats = ["protobuf"]
```

`itara verify`'s serializer-compatibility check confirms a connection's
serializer against its callee API through *either* of two independent
paths — the explicit `supported` entry above, or this
`[serializer.capabilities] message-formats` declaration matching the API's
`message-format`. Either alone is enough; this example happens to satisfy
both.

**`gateway-api/gateway-api.itara`** has no `[contract]` section and no
`[serializers]` section at all — deliberately. This is the ordinary,
unrestricted case: most APIs declare no message format and no serializer
list, and `itara verify`'s serializer-compatibility check stays silent for
them, exactly as it should (spec §8.6).

## The wiring: plugging in the proto serializer

The one connection between components in this example, in `wiring.yaml`:

```yaml
connections:
  - id: "gateway-to-calculator"
    from: "gatewayNode"
    to: "calculatorNode"
    transport:
      id: "http"
      params:
        host: "localhost"
        port: "8081"
    serializer:
      id: "protobuf"
```

`serializer.id: protobuf` is the entire "plug in the proto serializer"
step — nothing else in the wiring config or either component's code
changes because of it. Swap this back to `id: json` (and drop the proto
plumbing from `calculator-api`) and the topology still wires up the same
way; only the bytes on the wire and the contract's parameter/return types
would differ.

## Building it

```bash
mvn clean install
```

`calculator-api`'s build compiles `calculator.proto` via
`protobuf-maven-plugin`, which resolves a matching `protoc` binary as a
Maven artifact through `os-maven-plugin` — no local `protoc` install
needed. `CalculatorRequest`/`CalculatorResponse` land in
`calculator-api/target/generated-sources/protobuf/java` and get compiled
alongside `CalculatorService.java` into `calculator-api`'s jar.

## Assembling the deployment layout

Same shape as every other Itara deployment — see the demo if this part is
unfamiliar:

```
deployment/
  lib/                                    ← shared classloader
    itara-core.jar
    itara-serializer-protobuf.jar

  agent/
    itara-agent.jar

  metafiles/
    calculator-api.itara
    calculator-impl.itara
    gateway-api.itara
    gateway-impl.itara
    itara-serializer-json.itara
    itara-serializer-protobuf.itara
    itara-transport-http.itara

  itara-libs/                             ← plugins, loaded at startup
    itara-transport-http.jar
    itara-serializer-json.jar

  wiring.yaml
```

This example uses a shared system classloader for the components,
so their jars don't need to be copied into the deployment directory,
they are added to the classpath in the startup commands.

`itara-serializer-protobuf`'s shaded jar bundles `protobuf-java` itself
(it's excluded only from `itara-core`, per that module's own `pom.xml`),
so it needs to be on the system classpath. The rest of the Itara plugins,
the HTTP transport and the JSON serializer, will be loaded by the
Itara-specific classloader for isolation.

## Running it

Two separate processes — this is a real HTTP round trip, not a colocated
call, so both need to be running.

**1. Start `calculator` first** (it needs to be listening before `gateway`
tries to call it):

```bash
java \
  -Ditara.nodes="calculatorNode" \
  -Ditara.config=deployment/wiring.yaml \
  -Ditara.metadata.dir=deployment/metafiles \
  -Ditara.lib.dir=deployment/itara-libs \
  -javaagent:deployment/agent/itara-agent.jar \
  -cp "deployment/lib/*:calculator/calculator-api/target/calculator-api-1.0-SNAPSHOT.jar:calculator/calculator-impl/target/calculator-impl-1.0-SNAPSHOT.jar" \
  dev.itara.runtime.ItaraMain
```

**2. Start `gateway`** in a second terminal, once `calculator` shows
`[Itara] component ready`:

```bash
java \
  -Ditara.nodes="gatewayNode" \
  -Ditara.config=deployment/wiring.yaml \
  -Ditara.metadata.dir=deployment/metafiles \
  -Ditara.lib.dir=deployment/itara-libs \
  -javaagent:deployment/agent/itara-agent.jar \
  -cp "deployment/lib/*:calculator/calculator-api/target/calculator-api-1.0-SNAPSHOT.jar:gateway/gateway-impl/target/gateway-impl-1.0-SNAPSHOT.jar:gateway/gateway-api/target/gateway-api-1.0-SNAPSHOT.jar" \
  dev.itara.runtime.ItaraMain
```

## What to expect

`gateway` is configured to start an HTTP listener with JSON serializer
and call `calculator` for each request. You can call `gateway` to trigger
the calculations via simple cURL commands:

```
curl -X POST http://localhost:8080/itara/gateway/sum \
     -H "x-itara-dispatch-key: external-to-gateway" \
     -H "x-itara-target-method: sum" \
     -d "[6, 12]"
```

That number crossed a real process boundary as protobuf-encoded bytes —
`GatewayClientImpl` built a `CalculatorRequest`, `gateway`'s outbound proxy
handed it to the proto serializer, the proto serializer called its
`toByteArray()`, the HTTP transport carried the bytes to `calculator`'s
process, its dispatcher handed them to the proto serializer's
reflection-based `parseFrom()` to reconstruct a `CalculatorRequest`,
`CalculatorServiceImpl.add()` ran with no idea any of that happened, and
the response made the same trip back.

Both processes will keep running, `Ctrl+C` both when you're done.

## Verifying the metadata is consistent

To inspect and verify the wiring config and metadata, you can use
the CLI tooling, which is part of Itara. The binary is built as
part of the Rust implementation:

```bash
cd rust && cargo build --release
```

Run the above command in the repo root, and it will build the Rust
implementation, including the CLI tool, which you can find at
`rust/target/release/itara` from the repo root.

```bash
itara verify deployment/wiring.yaml --metadata-dir deployment/metafiles
```

Should report clean — both the explicit and capability paths are
satisfied for the `calculator` connection, and `gateway`'s own API
declares nothing that would trigger the check at all. Try changing
`calculator-api.itara`'s `message-format` to something else, or removing
its `[serializers] supported` entry entirely, to see the WARNING (never an
ERROR) this check produces when neither path holds.
