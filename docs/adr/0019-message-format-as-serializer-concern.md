# ADR 0019 — Message Format as a Serializer Concern, Not a Transport or Contract Replacement

**Status:** Accepted
**Date:** July 2026

---

## Context

Contracts in Itara are plain interfaces (spec §3.3); components communicate
via typed method parameters and return values. Serialization of these types
is already a separate, pluggable concern — the serializer converts typed
values to bytes, the transport carries bytes, and neither knows about the
other (ADR 0007).

Protocol Buffers is commonly associated with three distinct things at
once, depending on the framework: a wire-format serialization scheme, an
RPC/transport layer (gRPC, with generated client/server stubs from `.proto`
`service` definitions), and — in the conventional gRPC-idiomatic path — the
contract itself. Adopting proto without deciding where it sits risks
conflating three concerns Itara has deliberately kept separate: the
contract (spec §3.3), the transport (spec §7), and the serializer (spec §8).

A decision was needed on where proto — and any future structural message
format — fits in this layering, and how far its adoption reaches.

---

## Decision

Proto is adopted purely as a **message format** (spec §5.4) — a way of
generating the types used as a contract's method parameters and return
values — implemented via the existing serializer SPI (spec §8). It is not a
transport and does not replace or extend the contract mechanism.

A contract's method signatures remain a plain, hand-written interface
(spec §3.3) regardless of message format. When an API artifact declares
`message-format = "protobuf"`, the *types* appearing in that interface's
signatures are generated by protoc from `.proto` message definitions — the
interface itself is unchanged in form.

Message-format adoption is all-or-nothing per API artifact: every method
on a proto-format artifact MUST use proto-generated types; mixing is not
permitted within one artifact. A single fact — the artifact's declared
`message-format` — answers the question for every method, rather than
requiring per-method inspection.

Message classes are generated at build time via protoc. There is no
runtime descriptor or reflection-based approach.

A full gRPC transport (HTTP/2, generated client/server stubs, streaming) is
explicitly out of scope for this decision and is deferred as a separate,
independent effort.

---

## Reasoning

**Scoping proto to the serializer layer preserves every existing
guarantee.** A component using message-format-generated types is still
directly callable in-process (spec §3.3), works over any transport — direct,
HTTP, Kafka — without modification, and costs nothing beyond changing what
the parameter and return types are.

**Treating proto as a transport would have broken ADR 0007's separation.**
It would have meant either replacing Itara's transport abstraction with
gRPC's specifically, or building a parallel connection path just for proto
— both undermine the "any serializer with any transport" guarantee that
ADR 0007 established.

**Treating `.proto` `service` definitions as the contract itself would have
handed contract ownership to generated code.** This is the conventional
gRPC-idiomatic approach, and it was rejected because it reintroduces
exactly the coupling between contract and wire format that ADR 0007
removed for transport and serializer — the contract would no longer be a
plain, hand-written interface, and every proto-based connection would be
inherently a gRPC connection, closing off "proto over HTTP" or "proto over
Kafka."

---

## Alternatives considered

**Dynamic/reflection-based proto handling** (`DynamicMessage`, a runtime
`.proto` descriptor). Rejected: too verbose, requires shipping and loading
a descriptor at runtime, and doesn't match how proto is normally used.

**Protostuff or similar reflection-based libraries claiming proto-wire
compatibility.** Rejected: not strictly proto-compatible, undermining
interoperability with genuine proto consumers — other languages, schema
registries, external tooling.

**Proto `service` definitions and generated client/server stubs as the
contract mechanism.** Rejected — see Decision and Reasoning above. This is
the standard gRPC-idiomatic approach and was the most seriously considered
alternative; it was rejected specifically because it bundles transport and
contract concerns that the specification keeps separate elsewhere.

---

## Consequences

- A component's business logic is unaffected by whether its API artifact
  declares `message-format = "protobuf"` or uses plain language types — the
  interface and the calling code are identical either way.
- Error payload handling is unaffected by message format: the payload
  remains transport-carried (spec §6.6.5) and is never itself a
  message-format-generated type (spec §6.6.2). How a serializer satisfies
  its obligation to handle the error payload is out of scope for this
  decision.
- A future gRPC transport is expected to compose with this decision rather
  than depend on it — an API artifact declaring `message-format =
  "protobuf"` today should work over a future gRPC transport without any
  change to the contract or the message-format declaration.
- This decision does not itself determine whether a serializer not built
  for a given message format may still be configured against it, or how
  tooling evaluates that combination. That is a separate, later decision.
