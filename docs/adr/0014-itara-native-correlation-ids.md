# ADR 0014 — Itara-Native Correlation IDs for Multi-Observer Correlation

**Date:** June 2026
**Status:** Accepted
**Supersedes:** ADR 0004

## Context

The current observability model requires all active observers to share the same `traceId` and `spanId` values, because those IDs are generated by the OTel bridge and copied into `ItaraContext`. This makes OTel a structurally privileged observer — it dictates the ID space that all other observers must conform to.

This creates two problems. First, any observability system that wants to manage its own ID lifecycle — Datadog, a custom audit log, a future Orca observer — must either accept OTel-dictated IDs or be correlated by other means. Second, if OTel is disabled, the ID generation strategy changes entirely — passive observers receive different-shaped IDs depending on whether the OTel bridge is present.

The root cause is that correlation between observers was solved by forcing identity — same IDs everywhere. The correct solution is correlation through stable Itara-native keys that are independent of any observer's internal ID model.

## Decision

The `ObservabilityFacade` generates two stable Itara-native IDs at the start of every call chain. These IDs are generated by the facade, not by any bridge, and are present in every event fired to every observer regardless of which bridge or observers are active.

**`itaraTraceId`** — stable for the lifetime of the originating request. Every span in the same logical call chain carries the same `itaraTraceId`, whether it crosses one process boundary or ten. This is the join key for correlating everything that belongs to one operation across all observers.

**`itaraSpanId`** — unique per component invocation. Changes at each call boundary, identifying the specific interaction between two components at a specific point in time. This is the join key for correlating a single span across observers — for example, finding the audit log entry that corresponds to a specific OTel span.

Both IDs are propagated across process boundaries in the Itara transport headers alongside the W3C trace context. Both are present as fields on `ItaraContext`, which every observer already receives.

Each observer is then free to maintain its own internal context and ID model. OTel manages its own `traceId`/`spanId` tree. Datadog manages its own. A custom audit log uses whatever ID scheme it needs. All of them receive `itaraTraceId` and `itaraSpanId` as standard fields on every event and can join on them after the fact.

The OTel bridge retains its current role for W3C context propagation and span lifecycle management. It loses its role as ID authority — IDs that matter for cross-observer correlation are Itara's responsibility, not OTel's.

## Consequences

- All observers are equal citizens. No observer is structurally privileged in the ID space. OTel can be enabled or disabled without affecting the correlation model available to other observers.
- `itaraSpanId` enables direct, unambiguous joins between observers. An auditor holding an OTel trace can locate the corresponding audit record by `itaraSpanId` without timestamp matching or component-name heuristics. This is directly relevant in regulated environments where audit trails must be traceable to specific component interactions.
- `itaraTraceId` enables full chain correlation even when observers instrument at different granularities. A client application using the OTel observer directly, creating spans not visible to other observers, can still be correlated with Itara's topology-aware spans through the shared `itaraTraceId`.
- Custom and future observers — Datadog, Orca, audit logs — can be correlated with OTel traces without sharing OTel's internal IDs or depending on OTel being present.
- The `ItaraObserver` SPI contract is unchanged structurally. `itaraTraceId` and `itaraSpanId` are added as fields to `ItaraContext`, which observers already receive on every event.
- Every transport implementation must propagate Itara headers — including `itaraTraceId` and `itaraSpanId` — across process boundaries. A transport that does not propagate these headers breaks cross-process correlation for all observers. This is a conformance requirement for transport implementations, not an optional feature.
- The OTel bridge implementation requires a minor update: it no longer seeds the correlation fields in `ItaraContext`, it reads them. The bridge continues to manage OTel's own span lifecycle and W3C traceparent propagation independently.
- Observers that cannot store custom attributes can fall back to receiving the full `ItaraContext` as they do today, using the W3C IDs if needed. The Itara-native IDs are additive, not a replacement.
